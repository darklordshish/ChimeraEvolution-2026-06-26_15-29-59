# Claude Code memory options: built-in, plugins, MCP servers, parallel-session patterns (research date 2026-11-10)

## 1. Claude Code built-in memory (CLAUDE.md, rules, auto memory, skills) and Anthropic API memory tool

### Takeaway
Claude Code already ships two layers: hand-written instructions (CLAUDE.md hierarchy, imports, path-scoped rules) and Claude-written auto memory. Auto memory is the same design as ours (MEMORY.md index plus topic files with user/feedback/project/reference types), so our setup is essentially the native mechanism. The auto memory directory is machine-local and shared by all worktrees of a repo. The API memory tool is a separate, client-side feature for apps built on the API, not for Claude Code itself.

### Cited Findings
- Two mechanisms carry knowledge across sessions: CLAUDE.md files (you write) and auto memory (Claude writes). Both load at session start; Claude treats them as context, not enforced config. For hard enforcement use a PreToolUse hook. — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- CLAUDE.md locations: managed policy (Windows `C:\Program Files\ClaudeCode\CLAUDE.md`), user `~/.claude/CLAUDE.md`, project `./CLAUDE.md` or `./.claude/CLAUDE.md`, local `./CLAUDE.local.md` (gitignored). Files in the directory tree above the working dir are loaded at launch and concatenated from filesystem root down to cwd. Subdirectory CLAUDE.md files load on demand when Claude reads or edits files there. — [docs: memory](https://code.claude.com/docs/en/memory)
- Imports: `@path/to/file` syntax, relative paths resolve from the importing file, recursive up to 4 hops, skipped inside code spans/fences. Imports outside the working directory trigger a one-time approval dialog for project files. — [docs: memory](https://code.claude.com/docs/en/memory)
- Size guidance: target under 200 lines per CLAUDE.md. Multi-step procedures or part-of-codebase facts should go to skills or path-scoped rules. Docs recommend periodic review for contradictory instructions (Claude may pick one arbitrarily); `/doctor prompt-audit` can audit CLAUDE.md, rules, skills, subagents. — [docs: memory](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md`: discovered recursively, one topic per file; frontmatter `paths:` globs make a rule load only when matching files are touched. Symlinks supported for sharing rules across projects (external symlinks need approval). User-level rules in `~/.claude/rules/`. — [docs: memory](https://code.claude.com/docs/en/memory)
- Path-scoped rules for a sibling git worktree load only if the session is started in (or moved with `/cd` to) that worktree. A gitignored `CLAUDE.local.md` exists only in the worktree where it was created; docs suggest importing a file from the home directory to share personal instructions across worktrees. — [docs: memory](https://code.claude.com/docs/en/memory)
- `claudeMdExcludes` setting skips ancestor CLAUDE.md files by glob (all settings layers, arrays merge). `--add-dir` does not load CLAUDE.md from extra dirs unless `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. — [docs: memory](https://code.claude.com/docs/en/memory)
- AGENTS.md: since Claude Code v2.1.277 it is read directly, but by default only when no CLAUDE.md/CLAUDE.local.md exists in cwd or above; a CLAUDE.md can `@`-import AGENTS.md; a setting `claude-md-and-agents-md` loads both. `.agents/` directories and AGENTS.local.md are not read. — [docs: memory](https://code.claude.com/docs/en/memory)
- Auto memory: on by default in local sessions; toggle `/memory` or `autoMemoryEnabled`, env `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Claude saves four types recorded in frontmatter `type`: user, feedback, project, reference; it skips what is derivable from code or already in CLAUDE.md. — [docs: memory](https://code.claude.com/docs/en/memory)
- Storage: `~/.claude/projects/<project>/memory/` with `MEMORY.md` index (one line per memory) plus topic files. `<project>` derives from the git repo, so all worktrees and subdirs share one directory. Machine-local, not shared across machines. Excluded from transcript cleanup. Relocatable with `autoMemoryDirectory` (absolute or `~/` path; settable in any settings scope). `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+) lets projects share one directory. — [docs: memory](https://code.claude.com/docs/en/memory)
- Load limit: only the first 200 lines or 25 KB of MEMORY.md load at session start; after writes Claude Code warns when near the limit and errors when over it. Limit applies to MEMORY.md only; CLAUDE.md files load whole up to 4 MiB. — [docs: memory](https://code.claude.com/docs/en/memory)
- Subagent persistent memory: frontmatter `memory: user|project|local` gives a subagent its own directory (`~/.claude/agent-memory/<name>/`, `.claude/agent-memory/<name>/` committed to git, or `.claude/agent-memory-local/<name>/`), also with the 200-line/25KB MEMORY.md rule. It depends on auto memory being enabled. `project` is the recommended default. — [docs: sub-agents](https://code.claude.com/docs/en/sub-agents)
- Skills are the docs' stated home for multi-step procedures (procedural memory), loaded on demand rather than every session. — [docs: memory](https://code.claude.com/docs/en/memory)
- API memory tool (`memory_20250818`, name `memory`): stable, client-side. Claude issues commands (view, create, str_replace, insert, delete, rename) on a `/memories` path and your app executes them against storage you control. SDK helpers exist (`BetaLocalFilesystemMemoryTool` in Python/TS). Docs warn about path traversal and recommend size caps/expiration. It requires you to write your own agent loop; it is not a Claude Code feature. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Anthropic's recommended multi-session pattern for the memory tool: an initializer session creates a progress log, feature checklist and startup script reference; each later session reads them first and updates the progress log before ending; mark features complete only after end-to-end verification. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Context editing (beta header `context-management-2025-06-27`): `clear_tool_uses_20250919` (default trigger 100k input tokens, keep 3) and `clear_thinking_20251015`; Claude is warned to save to memory before results are cleared. Server-side compaction (`compact_20260112`) is recommended for long conversations. API-level features, not user-facing in Claude Code. — [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Anthropic reports memory tool plus context editing gave +39% vs baseline, context editing alone +29% (an agentic-search eval, vendor-reported) — [Anthropic: context management](https://www.anthropic.com/news/context-management?q=october), via search snippet only (not fetched).

### Inferences
- Our file-based setup (MEMORY.md one line per entry, one file per fact, types user/feedback/project/reference, ~55 entries) is exactly the documented auto memory layout, so nothing needs installing to keep it. The 200-line/25KB cap is the real ceiling to watch: with ~55 long one-line entries (ours are very long lines) the index may already be near 25 KB. Worth measuring the byte size of MEMORY.md.
- Because the directory is keyed to the git repo and shared by all worktrees, our "slices" cannot come from auto memory scoping; they must be done by file naming/prefix, subdirectories (topic files can live anywhere under the directory, only MEMORY.md is auto-loaded), or path-scoped `.claude/rules/` files with `paths:` per line (modeli/les) committed to git.
- Project-scope subagent memory (`.claude/agent-memory/<name>/`) is a native way to give a per-role slice (e.g. a "model-critic" agent) that is git-versioned, unlike auto memory.
- Codex/opencode cannot read Claude's auto memory natively; AGENTS.md is the common denominator (Claude reads it directly only if no CLAUDE.md exists, otherwise via `@AGENTS.md` import). Our repo has an untracked AGENTS.md already.

### Gaps
- Exact byte size/line count of our MEMORY.md was not measured here (outside research scope).
- Whether auto memory writes use any locking when several sessions write concurrently: docs say nothing found.
- Official guidance specifically on "partitions/slices" of memory: none found; docs only describe user/project/local scopes.

## 2. Community plugins/skills and MCP memory servers

### Takeaway
Options split into (a) hook-based auto-capture plugins (claude-mem; needs an LLM to compress, so not purely local-free unless using own key or Claude plan), (b) file-based/markdown MCP servers (Basic Memory, local, AGPL, partitions via "projects"), (c) knowledge-graph/vector servers (official @modelcontextprotocol/server-memory is simplest and truly local; Graphiti and mem0/OpenMemory need Docker and an LLM, local only with Ollama). None offers git-friendly, human-curated, one-line-index memory better than what we have; their value would be search over a much larger corpus.

### Cited Findings
- claude-mem (thedotmack/claude-mem): plugin that records observations via a second agent, compresses and injects a compact index into later sessions. Repo page shows ~115.6k stars, version badge 15.15.1, Apache-2.0 (one aggregator says AGPL-3.0; other search snippets cite 32.1k stars in Feb 2026 and 51k elsewhere, so star counts vary by date and licence needs verification). Storage: SQLite at `~/.claude-mem/claude-mem.db` plus Chroma for semantic search; local unless opt-in cloud sync. It calls an LLM to compress: options are claude-mem's hosted observer (sign-in, 30-day free trial), own OpenRouter/Gemini key, or your Anthropic plan. Anonymous telemetry on by default (disable with `npx claude-mem telemetry disable`). Node 20.19+/22.12+. Install: `npx claude-mem install` or `/plugin marketplace add thedotmack/claude-mem` then `/plugin install claude-mem`. Scoping is "for this project"; by default session-start context limited to the current harness, setting `CLAUDE_MEM_SESSION_START_INCLUDE_ALL_SOURCES=true` merges all harnesses. — [GitHub: claude-mem](https://github.com/thedotmack/claude-mem); licence/stars discrepancies from [search results](https://shiporskip.io/compare/claude-code-local-mlx-apple-silicon-offline-2026-vs-claude-mem-persistent-memory-compression-claude-code-sessions-sqlite-vector-2026) and [awesome.ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fthedotmack%2Fclaude-mem)
- Impostor warning: a github.com/sloki13/claude-mem page is headed by token-trading links; do not use. Forks like bjarne56/claude-mem-plus add self-hosted cross-machine sync. — [search results](https://github.com/sloki13/claude-mem)
- Official `@modelcontextprotocol/server-memory`: knowledge graph of entities, relations, observations; 9 tools (create_entities, create_relations, add_observations, delete_*, read_graph, search_nodes, open_nodes). Stored in a local JSONL file (`memory.jsonl`), path via `MEMORY_FILE_PATH`. Atomic saves and a `.lock` file serialize writes from multiple processes, so several clients can share one file (not safe on network filesystems; 60 s lock timeout). Requires Node.js 24+ via npx. Default path sits inside the package dir and can be wiped on reinstall, so set the path explicitly. No built-in partitions; use separate files per slice (separate server instances with different `MEMORY_FILE_PATH`) or entity-type conventions. No LLM or API needed. — [GitHub: servers/src/memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)
- Basic Memory (basicmachines-co/basic-memory): MCP server, notes as local Markdown files plus local SQLite index (Postgres optional), AGPL-3.0, ~4.5k stars, Python 3.12+, installed with `uv tool install basic-memory` / `uvx basic-memory mcp`. Multi-project support (project-scoped tools take project name). Tools: write/read/edit/move/delete, search, list, context (graph), project, schema. Editable in Obsidian. Hosted cloud sync/teams is paid ($15/mo) and optional; local is free with no account. Version listings conflict (v0.20.2, v0.22.1, "0.23" in README); page gave no release date. Whether several clients can share one local instance was not stated. — [GitHub: basic-memory](https://github.com/basicmachines-co/basic-memory); [directory listing](https://mcpplaygroundonline.com/mcp-servers/io-github-basicmachines-co-basic-memory)
- Graphiti MCP server (getzep/graphiti, mcp_server): temporal knowledge graph. Default FalkorDB in one Docker container (Neo4j 5.26+ alternative). Needs an LLM and embedder: OpenAI by default; Anthropic, Gemini, Groq, Azure supported; Ollama works via OpenAI-compatible endpoint, but README warns small local models often produce JSON that fails schema checks. `group_id` namespaces data (own graph per group on FalkorDB, default "main") — a native partition concept. README calls it a reference implementation with no auth, not for production. Setup: `docker compose up` with `.env` key. — [GitHub: graphiti mcp_server](https://github.com/getzep/graphiti/tree/main/mcp_server)
- mem0 / OpenMemory: official OpenMemory runs as Docker stack with Qdrant default and needs an OpenAI key unless switched to local LLM; API on localhost:8000. Community wrappers (e.g. elvismdev/mem0-mcp-selfhosted) run on self-hosted Qdrant, Neo4j and Ollama, with `MEM0_PROVIDER=ollama` removing the Claude/OpenAI dependency. Mem0's own hosted MCP stores data in a Mem0 account (cloud-only). — [mem0 OpenMemory docs/search](https://docs.mem0.ai/openmemory/quickstart); [glama listing](https://glama.ai/mcp/servers/elvismdev/mem0-mcp-selfhosted); [unabyss roundup](https://unabyss.com/blog/best-memory-mcp-servers-claude)
- A third-party roundup states built-in auto memory or claude-mem covers a single repo well, while shared memory services need MCP servers — secondary source, unverified. — [unabyss](https://unabyss.com/blog/best-memory-mcp-servers-claude)

### Inferences
- Rough free-and-local ranking by setup effort: (1) native auto memory + rules/skills (zero); (2) official server-memory with per-slice `MEMORY_FILE_PATH` (one npx line per slice; needs Node 24); (3) Basic Memory (uv + Python 3.12; closest to our markdown-files design, AGPL but irrelevant for local use); (4) claude-mem (one command, but ongoing LLM calls cost tokens on your Claude plan or a third-party key, and auto-captured noisy observations); (5) Graphiti / OpenMemory (Docker plus LLM plus embeddings; heaviest, risky with local small models).
- Hook-based capture (claude-mem) makes memory nobody curates; for a team of 3-4 sessions with strong provenance rules (СТАТУС.md, spec status detectors) uncurated machine summaries risk stale/contradictory facts, the exact pitfall our docs try to prevent.
- Windows 11 host: Docker-based options add Docker Desktop dependency; Python/uv or Node options are lighter. Not verified on Windows for any of these.

### Gaps
- Not covered by evidence found: Letta MCP, Chroma/sqlite-vec-based MCP servers, and "consolidate-memory"-style skills beyond the fact that a built-in `consolidate-memory` skill exists in our environment's skill list (reflective pass: merge duplicates, fix stale facts, prune index) — no external source fetched.
- Exact current releases/dates for Basic Memory and Graphiti, and the claude-mem licence, were not confirmed from primary pages.
- Hands-on reliability, Windows compatibility, and concurrent-session behavior of any of these were not tested.

## 3. Patterns for parallel sessions on one repo and known pitfalls

### Takeaway
Worktrees isolate source code only: Claude's auto memory and `~/.claude` state stay shared, which causes silent overwrites (stale-read last-write-wins). Community fixes are per-session namespaces/subdirectories, file locking, heartbeat claims, handoff/progress files and keeping 2-3 sessions.

### Cited Findings
- Case report: 3 parallel Claude Code sessions over 8 hours; two silent overwrites in shared `~/.claude/` state. A skills index entry vanished (read-then-write race) and `architecture.md` memory notes were replaced by a session writing from a stale cached copy. About $47 in tokens and ~40 min to re-derive. Fixes: per-worktree CLAUDE.md directing memory writes to a branch-specific subdirectory merged at session end; ~20-line `flock` wrapper for shared files; optional heartbeat files `~/.claude/sessions/<pid>.json` declaring branch and touched files. — [dev.to: kenimo49](https://dev.to/kenimo49/i-ran-3-claude-code-sessions-in-parallel-for-8-hours-they-overwrote-each-others-context-twice-4bba)
- Auto memory is "per repository, shared across worktrees" per Anthropic docs, so a wrong correction in one session can carry into others. — [docs: memory](https://code.claude.com/docs/en/memory); pitfall framing from [memorylake write-up](https://www.memorylake.ai/blogs/claude-code-worktrees-memory)
- CLAUDE.md comes from each worktree's own checkout: uncommitted instruction changes do not reach new worktrees (a `.worktreeinclude` pattern copies a file once at creation). — [search summary of community guides](https://www.mindstudio.ai/blog/claude-code-git-worktree-parallel-branches)
- Handoff-file collisions: two sibling sessions can pick the same next handoff number in `docs/handoffs/` because each sees only its own branch; recommended to detect and renumber before pushing. — [agent-traffic-control plugin listing](https://www.claudepluginhub.com/plugins/wan-huiyan-agent-traffic-control-plugins-agent-traffic-control)
- Other practices cited: claim protocol for issues, check for orphaned branches/PRs before starting, 2-3 parallel sessions as sustainable ceiling, conflicts surface only at merge time. — [search summaries: verdent, mindstudio](https://www.verdent.ai/guides/how-to-run-parallel-claude-code-agents)
- Anthropic's own pattern for multi-session work: progress log, feature checklist, update log before session end, completion only after end-to-end verification. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); long-form case study "Effective harnesses for long-running agents" referenced there (not fetched).

### Inferences
- Our conventions already cover the main mitigations: one line = one worktree = one branch; git-tracked docs (СТАТУС.md, УКАЗАТЕЛЬ.md, specs with status rules) act as the shared source of truth; letters `FEEDBACK-*.md` act as handoff notes. The unmitigated risk is the shared auto-memory directory, which is not in git: no history, no merge, last-write-wins. Mitigations to consider: (a) per-line file name prefixes or slice subdirectories with MEMORY.md index lines written only by the owning line; (b) commit a snapshot of memory to git periodically or move it under the repo via `autoMemoryDirectory` (then diffs and blame exist, but beware memory contents becoming project-shared across Codex/opencode); (c) a dated-fact convention plus consolidation pass to catch stale entries.
- Stale-facts pitfall is real for 55+ entries with absolute dates in text; memory entries describing state ("ready/in main") rot fastest, and the docs themselves tell Claude to skip what can be derived from code or git.

### Gaps
- No primary-source (Anthropic) guidance on concurrent writes to the memory directory found.
- Most pitfall evidence is single-author blog posts/aggregators, not reproducible studies.
- No evidence gathered on how Codex/opencode read or write a shared memory directory.
